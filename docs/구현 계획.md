# 구현 계획

## 1. 구조
```
streamlit_app.py   화면(로그인, 학생 화면, 관리자 화면). key는 공고 2.7절 표 그대로
services.py        업무 로직(명단, 로그인, 지원, 투표, 마감, 배정안 저장, 확정) — 한 트랜잭션 + lock
rules.py           규칙(필수 역할 계산, 지원·승인 검사, 배정안 검사 5가지, 완전 탐색 배정, 배정 불가 이유)
ai.py              오픈라우터 호출(1~3차 모델, 120초 전체 대기 제한, 응답 읽기, 실패 처리)
db.py              DB 연결 풀(psycopg_pool), 상태를 질의 1번으로 읽기, 시험용 sqlite
security.py        bcrypt 비밀번호 해시
schema.sql         tf_ 테이블(앱이 시작할 때 그대로 실행)
tests/             연습 시나리오 3개 시험, AI 실패 처리 시험, 화면 연기 시험
.github/workflows/keepalive.yml   매일 DB 질의(일시정지 막기)
```

## 2. DB 설계(공고 5장 최소 참고안 + 확장)
- `tf_students`(학번 유일, bcrypt 해시, is_admin), `tf_student_sub_roles`, `tf_teams`(team_no 유일),
  `tf_members`((team_id, slot_no) 기본 키, student_id 유일, slot_no 1~4 check),
  `tf_applications`(대기/승인/거절, 이유, 시각), `tf_votes`((application_id, voter_id) 기본 키), `tf_settings`.
- 늘린 것: `tf_ai_logs`(AI 호출 기록), 지원의 `reason`·`decided_at`,
  "한 학생은 대기 지원 1개만"을 지키는 부분 유일 인덱스(`where status = '대기'`).
- 역할 열에는 6개 역할만 허용하는 check.

## 3. 동시성
- 바꾸는 작업은 모두 `pg_advisory_xact_lock`을 잡은 트랜잭션 안에서 "상태 읽기 → 규칙 검사 → 기록" 순으로 한다.
  → 같은 팀에 동시에 눌러도 차례로 처리되고, 두 번째 학생은 갱신된 상태로 검사된다.
- 그래도 빠져나가는 경우를 위해 DB 유일성 제약(자리, 학생 1팀)이 마지막으로 막는다.

## 4. 규칙 구현 요점
- 필수 역할 채움 수 = {기획자 가능자, 웹 프로그래머 가능자}에서 서로 다른 두 사람을 고를 수 있는지(0~2).
- 필수 포함 역할 자리: 들어간 뒤 남는 자리 < 아직 못 채운 필수 역할 수 → 막힘(지원할 때와 승인 직전에 같은 함수).
- 승인 직전 검사: 마지막 찬성이 들어온 순간 정원·주 역할 중복·필수 역할 자리를 다시 검사.
- 완전 탐색 배정: 넣을 수 있는 팀이 적은 학생부터, 정원·주 역할 중복으로 가지치기, 필수 역할 자리와 최소 인원으로 가지치기,
  실패한 상태(팀 상태 요약)를 기억해 같은 탐색을 되풀이하지 않음. 없으면 이유를 찾아 설명.

## 5. AI 배정 흐름
1. 마감 확인 → 완전 탐색으로 "규칙을 지키는 배정이 있는지" 먼저 확인. 없으면 이유를 `assign_status`에 보여 주고 끝(AI 안 부름).
2. 1차 모델 호출: 별도 스레드로 요청하고, 본 스레드가 1초마다 경과 시간을 재며 "1차 모델(이름)의 응답을 기다리는 중… n초/120초"를 표시.
   120초가 넘으면 기다리지 않고 다음 모델로(요청 timeout 값만으로는 응답이 천천히 오면 120초를 넘길 수 있어서).
3. 응답 → JSON 읽기 → 검사 5가지. 빈 응답·오류(HTTP 429 등)·JSON 아님·검사 실패는 모두 실패로 기록하고 다음 모델로.
4. 3차까지 실패하면 앱이 완전 탐색으로 배정. 모든 시도는 `tf_ai_logs`에 남기고 관리자 화면에 표로 보여 줌.
5. 검사를 통과한 배정안만 관리자에게 보여 주고, 확정할 때 다시 검사한 뒤 저장.
- 요청에는 `reasoning: {effort: low}`와 넉넉한 `max_tokens`를 줌(빈 응답 줄이기). `openrouter/free`는 쓰지 않음.

## 6. 화면
- 학생 화면: whoami, (fragment 3초 자동 갱신) result, 팀 카드 `team_N` + `apply_N`, 내 팀에 들어온 지원 + `vote_yes_/vote_no_{학번}`.
- 관리자 화면: whoami, result, 명단(`admin_roster_file`, `admin_team_count`, `admin_start`), `admin_close`,
  `admin_assign`, `assign_status`(진행·배정안·배정 불가 이유), `admin_confirm`(배정안이 있을 때만),
  (fragment 3초 자동 갱신) 팀 카드와 `unassigned`, AI 호출 기록, 설정 확인(비밀 값은 있음/없음만).
- 관리자 단추는 학생 화면에 없고, 눌렀을 때도 DB에서 관리자인지 다시 확인.

## 7. 시험 계획
1. `python tests/test_scenarios.py`: 부록 1~3의 모든 단계를 업무 로직으로 실행해 결과 첫 단어를 비교, 확정 뒤 규칙 검사.
2. `python tests/test_ai.py`: 1차 429 → 2차 검사 실패 → 3차 시간 초과 → 앱 자체 배정, 2차 성공 시 멈춤, 응답 읽기.
3. `python tests/smoke_ui.py`: Streamlit 흉내 모듈로 화면 코드를 실행해 key가 빠짐없이 나오는지, 콜백 결과를 확인.
4. 배포한 앱에서 연습 시나리오를 직접 실행하고 화면을 캡처(README 5~7항의 근거).

## 8. 배포
- 비공개 깃허브 저장소 → Streamlit Community Cloud(Main file `streamlit_app.py`, Branch `main`).
- Secrets: `OPENROUTER_API_KEY`, `DATABASE_URL`(Supabase Session pooler 주소), `ADMIN_PASSWORD`, (선택) `OPENROUTER_MODELS`.
- 깃허브 Actions Secret에 `DATABASE_URL`을 넣어 매일 DB 질의.
- 배포 뒤 Sharing을 public으로 바꾸고 시크릿 창에서 로그인 화면 확인.
